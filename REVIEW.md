## 1. Technical Rigor — Score: 3/10

### The circular labeling problem (Critical)

The ML classifier (`models.py`) is trained on labels generated by `add_weak_labels()`
in `features.py`. Those labels are produced by keyword heuristics — the same keyword
logic that Stage 1 rule-based routing already uses. The classifier therefore learns to
approximately replicate the keyword rules. It adds **zero new signal**.

Training accuracy will look artificially high because train/test splits both come from
the same deterministic rule. An interviewer who asks "what does your ML model actually
learn that rules don't?" will expose this immediately.

**Fix**: Use the Twitter dataset's actual labels or metadata as a proxy ground truth.
Better: label a 1,000-row sample manually, train on that, and benchmark against the
keyword baseline with a confusion matrix showing the delta.

### Uncalibrated confidence scores used as routing gates

`predict_with_confidence()` uses `max(softmax_proba)` from logistic regression as the
routing threshold signal. Logistic regression probabilities are **not calibrated** for
multi-class problems with class imbalance. A ticket can have `max_proba=0.87` on a wrong
label. The 0.85/0.55 routing thresholds are therefore empirically groundless.

**Fix**: Wrap the classifier in `CalibratedClassifierCV(cv=5, method='isotonic')` and
plot a reliability diagram. Tune thresholds on a validation set.

### DistilBERT script is a stub

`scripts/train_distilbert.py` loads a tokenizer, tokenizes 5,000 samples, and then
prints: *"Next step: add Trainer + TrainingArguments for full training loop."*
It does not train. This is listed in the README as a feature.

**Fix**: Either delete this file entirely (cleaner) or complete the `Trainer` loop with
`TrainingArguments`, an evaluation metric callback, and a saved checkpoint.
A half-finished script is worse than no script.

### LLM error handling is absent

In `routing.py`, Stage 3 calls `llm_classify_ticket(text)` with no try/except.
Inside `llm.py`, `json.loads(response.output_text)` will crash with `JSONDecodeError`
whenever the model wraps JSON in markdown (e.g., ` ```json\n{...}\n``` `).
One malformed response crashes the entire batch.

**Fix (15 min)**: Wrap with try/except, add regex extraction fallback
`re.search(r'\{.*\}', text, re.DOTALL)`, fall back to human queue on parse failure.

### New OpenAI client instantiated per call

`_client()` in `llm.py` is called inside every function body, creating a new
`OpenAI()` object (and underlying HTTP connection) for every ticket.

**Fix (5 min)**: Module-level singleton with lazy init.

## 2. Business Relevance — Score: 5/10

The 4-stage cascade (rule → ML → LLM → human) is architecturally sound and reflects
real production thinking. The queue names are contextually appropriate.

**What undermines it:**
- The rule-based stage has exactly **2 hard-coded strings** (`"refund"` and
  `"double charged"`). This is not a rule engine; it is an if-statement.
- `llm_summarize_ticket()` and `llm_resolution_and_escalation()` are defined but
  **never called** from the pipeline. They are dead code.
- The evaluation module is 19 lines. The cost formula is `0.001 + 0.02 * llm_rate` —
  a magic constant with no relationship to actual GPT-4.1-mini pricing per token.
- No urgency or complexity classifier is trained — those columns exist as weak labels
  but no model learns from them.

**What a PM interviewer at Google would ask**: "How do you measure routing quality?
What's the false-positive rate for the billing queue?" The code cannot answer this.

filter it out. The classifier is trained on agent-generated text, contaminating labels.

**Performance bug**: `route_dataframe()` iterates row-by-row, calling the sklearn
model one sample at a time. `Pipeline.predict()` is vectorized; this loop discards
that advantage entirely.

### B. Top 3 Fastest Fixes (Under 1 Hour Total)

**Fix 1 — LLM error handling (15 min)**  
In `llm.py`, wrap `json.loads()` in try/except, add regex JSON extraction, return a
safe default on failure. Wire a fallback in `routing.py` to send parse failures to
`human_triage_queue`. This is a one-function change that makes the pipeline robust.

**Fix 2 — Filter agent messages from training data (10 min)**  
In `data.py`, `build_unified_ticket_table`: add `.query("inbound == True")` before
processing the Twitter DataFrame. Removes systematic training contamination.

**Fix 3 — OpenAI client singleton (5 min)**  
Replace `_client()` with a module-level `_OPENAI_CLIENT = None` and lazy init on
first call. Shows you understand connection management and stateless function design.

### C. Top 3 Most Impressive Upgrades for Your Resume

**Upgrade 1 — Real evaluation with threshold optimization**  
Create a 500-row manually labeled eval set. Plot precision/recall per queue at multiple
confidence thresholds (0.5 to 0.95). Generate a cost-vs-accuracy Pareto curve showing
the optimal operating point. This transforms the project from "I built a thing" to
"I measured and optimized a thing" — the core gDATA skill.

**Upgrade 2 — Complete DistilBERT fine-tuning with a proper comparison**  
Finish `train_distilbert.py` with `Trainer` and `TrainingArguments`. Produce a
side-by-side table: TF-IDF+LR vs. DistilBERT on accuracy, inference latency (ms/ticket),
and estimated cost. Showing you understand the accuracy-vs-cost tradeoff of model
selection is directly relevant to Google production ML culture.

**Upgrade 3 — Wire LLM summarization and escalation into the dashboard**  
Actually call `llm_summarize_ticket()` for tickets routed to `human_triage_queue` and
display those summaries in the Streamlit app. Add a "Route This Ticket" interactive
input. Add escalation flags to the routed CSV. This makes the demo viscerally convincing
and completes two features that are currently dead code.

## Bottom Line

The architecture narrative is solid and shows genuine product thinking. But the
implementation has a structural flaw (circular labels), two dishonest features
(DistilBERT stub, dead-code LLM functions), and no honest measurement of whether the
system works better than keyword rules.

**Fastest path to interview-ready**:
1. Fix the labeling strategy (real ground truth, even 500 rows)
2. Add a real eval loop comparing rule-only vs. rule+ML vs. rule+ML+LLM
3. Delete or complete the DistilBERT script — no half-finished code
